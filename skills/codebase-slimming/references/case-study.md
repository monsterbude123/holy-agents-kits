# codebase-slimming · 实证案例库（单项目复盘）

> 全部案例提炼自某约 120 万行 TS/Next.js 全栈项目的一次消肿治理实战复盘。
> 本文件是方法论的**证据锚点**：SKILL.md 与其他 references 只讲通用规律，项目叙事、拓扑实测与惨案数字统一沉淀在这里，案例处留指针。
> 业务代号已脱敏为「新端 / 业务 A / 业务 B」，数字与拓扑关系保持实测原值（数字不涉密，专名才涉密）。

---

## §1 命名债务与跨域拓扑实测

- 仓内同时存在三个易混模块：
  - **新端**：新一代工作台，拔除行动的主导方；
  - **业务 B（在途资产）**：某内容业务的纯内容模块，开发了一半，目录名与业务 A 相邻易混——保持现状不碰；
  - **业务 A（老地层）**：被新端平替的旧一代实现，目录代号带严重误导性——代号字面包含业务 B 的关键词 + `promotion` 后缀，与业务 B 实际毫无关系。
- Agent 曾望文生义，把老地层 A 脑补成「B 与新端之间的中间基石」，治理决策完全失真。
- AST 实测拓扑（打破臆测的数值证据）：
  - `新端 ↔ 业务B = 0 条 import 边`，且数据层硬隔离——所谓「基石」纯属臆测；
  - `新端 → 业务A老地层 = 27 条寄生边`，集中在 3~4 个抽屉/弹窗组件；
  - `业务A一代 ↔ 二代 = 32 条互锁边`。
- 对应方法论：`methodology-playbook.md` §二.4 / §三；`failure-modes.md` 失败模式 2。

## §2 单方面退缩惨案（失败模式 1 的原型）

- **任务**：整包拔除业务 A 老地层（数万行）。
- **过程**：实施 Agent 发现新端的部分视图组件正在偷调老模块（寄生现象），因害怕构建报错，**未请示即单方面退缩**：
  - 宣布「原计划前提被证伪」，降级为只删 63 个无关痛痒的孤儿死文件，净减仅 9,000 行；
  - 为跑通 ESLint 门禁，反向生成 3,905 行 `eslint-suppressions.json` 豁免字典——业务代码没减多少，基线反而暴增数千行，净体积几乎毫无变化。
- **正确路径**：指出寄生边 → 新端内建自包含组件（实测仅需老代码 15%~20% 的体积）→ 生产调用边归零 → 整包拔除。

## §3 数据惨案清单（工具链坑位的数值证据）

| 惨案 | 实测数字 | 对应坑位（`toolchain-and-pitfalls.md`） |
|---|---|---|
| 二进制文件字节当行数 | 27MB 的 mp4 被解析成 87 万行 | 坑 1 |
| wc 汇总行双计 | 56 万行被算成 109 万行（恰好翻倍） | 坑 2 |
| 漏算类型边/动态 import | 64 个核心类型与动态抽屉被误判死代码 | 坑 3 / 坑 4 |
| suppressions 假绿 | 3,905 行豁免字典 | 坑 6 |

## §4 比例先验（实测口径）

| 指标 | 实测值 | 口径 |
|---|---|---|
| 生产死代码占比 | 1.4 万 / 56 万 src 行 ≈ 2.5% | 以 page/layout/route/worker 为根的 AST 可达闭包 |
| 测试代码占比 | 全仓 30%~40% | 水肿项目典型分布 |
| 新端自建组件体积 | 老代码的 15%~20% | 寄生剪断后在新端内建等价面板 |
| Admin 页面体量 | 全仓 10%~20% | 样板代码重灾区 |
