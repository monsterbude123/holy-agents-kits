# codebase-slimming · 巨石代码库消肿与安全拔除通用方法论

> 本手册提炼自大型 TS/Next.js 全栈项目（从 120 万行巨石消肿治理）实战复盘。
> 文中比例数字（死代码 1~3%、tests 占 30%~40%、自建组件为老代码 15%~20% 等）均为该单项目实测先验，仅作量级参考（完整实测口径见 `case-study.md` §4），换项目/换技术栈须重测。
> 适用于：业务功能不多但代码体量达数十万至百万行、多次治理效果不显、死代码与活地层混杂纠缠的复杂软件系统。
>
> ⚠️ **命名债务警示**：模块目录名/表名/历史代号可能带严重误导性（实测案例与拓扑数字见 `case-study.md` §1）。**判断模块归属一律以导入图 + 架构文档为准，严禁望文生义按目录名臆断业务归属**。

## 一、 核心认知：四大认知陷阱与事实真相

| 常见认知误区 | 实测真相与客观规律 |
|---|---|
| **误区 1：代码膨胀全是因为死代码没删** | **真相**：生产死代码（零可达）通常仅占 1%~3%。100 万行代码中死代码往往只有 1~2 万行，删完体感毫无变化。真正吃掉行数的是**多代历史产品地层并存、多套技术栈并存（堆新不删旧）**。 |
| **误区 2：jscpd 重复率仅 1.8%，说明没有代码克隆** | **真相**：Token 级工具只能查变量名完全一样的纯文本复制。开发者重抄业务流时改了参数名、换了状态机，**Token 匹配率极低（假象安全），但业务概念 90% 重复**。 |
| **误区 3：门禁全绿就代表治理完成** | **真相**：很多团队为了跑通门禁，生成了上千行的 `boundaries-allowlist` 或 `eslint-suppressions`，把错误合法化；代码没减几行，基线又暴增几千行。 |
| **误区 4：看到有引用就断定老代码不能删** | **真相**：新系统往往在全屏弹窗或局部抽屉里“偷调”老系统组件（寄生现象）。**有引用不等于老系统该留，而是说明新系统的解耦没做干净**。 |

## 二、 核心前置：代码分布现状全景摸底（The Panorama Inventory）

治理大型代码库绝不能两眼一抹黑。如果不摸清全景分布，就会陷入“盲人摸象”：看到一个目录大就误判为死代码，或者看到十几万行“平台层/其他”就当作不可动的黑盒。
动手治理前，**必须出齐以下五张全景账本**：

### 1. 全仓互斥四桶账本（整体宏观透视）
将全仓 tracked 文件划分进四个互斥的桶，明确生产、测试与工程资产的比例：
- **产品代码（src）**：真正的生产运行时面（通常占全仓总代码行的 40%~50%）；
- **测试代码（tests）**：单测、集成测试、契约测试（水肿项目中测试常占 30%~40%）；
- **工程与门禁（scripts / gates）**：构建脚本、守卫门禁、迁移工具（通常占 5%~10%）；
- **过程资产与原型（.design / docs / prisma / packages 等）**：设计原型、文档、协议包。

### 2. src 产品域行数排行榜（微观业务透视）
按目录前缀与架构边界，将 `src/` 细分为 5~10 个核心业务域，计算物理行数与占比。
- **作用**：看清代码体量的物理大头究竟分布在哪些业务线，看清是“多产品域并存”还是“单点臃肿”。

### 3. 巨型模糊大桶的“二阶下钻”（破除黑盒迷雾）
当分域统计中出现体量 >10 万行（或占 src 25% 以上）的“平台层/其他”大桶时，**严禁笼统放过，必须进行二阶下钻**，拆分为四类性质：
1. **真平台底座**（如任务队列、错误码字典、项目基础 API）：全站依赖骨架，不可动；
2. **独立产品功能运行时**（如 AI 助手、独立工具引擎）：活的产品功能，非废料；
3. **误分类产品域**（如资产中心、用户配置页、工具箱）：属于记账漏标，需正名重新归域；
4. **架构固有长尾胶水**（如框架页面级 hooks、小路由、类型守卫）：小文件长尾，不可单删。

### 4. 跨域真实依赖拓扑矩阵（验证交集与寄生引线）
以 AST 导入图为依据，统计各核心域之间的双向 `import` 边数：
- **证实"零交集"**：两域 import 边为 0，以数据实证彻底独立，打破"A 域是 B 域基石"的伪认知（实测案例见 `case-study.md` §1）；
- **锁定"寄生边"**：新端指向老地层的每一条 import 边，都是拔除前新端必须自立的解耦点（实测 27 条集中在 3~4 个组件，见 `case-study.md` §1）；
- **排查"反向互锁"**：老地层内部新旧两代之间的互锁边，看清交缠程度。

### 5. 生产死代码 AST 可达闭包（锁定死代码上限）
以所有 `page/layout/route/worker` 为根节点做可达闭包，计算绝对死代码：
- 客观规律：在几十万行以上的系统中，真正的生产死代码通常仅占 **1%~3%**（如 56 万行中仅 1.4 万行）；
- **警示**：死代码比例 ≤3% 时，立即将治理重心转向“老地层平替与整包拔除”，绝不把时间浪费在死代码上。

## 三、 三权分立分析法（动手前的领域边界切分）

在摸清全景分布后，必须自顶向下完成业务三权分立，**严禁胡子眉毛一把抓**：

```
                    【全仓资产透视与三权分立】
                               │
     ┌─────────────────────────┼─────────────────────────┐
     ▼                         ▼                         ▼
【1. 在途资产】            【2. 平台核心】           【3. 已平替老地层】
(In-flight Assets)         (Platform Core)          (Obsolete Generation)
例如：开发了一半的独立功能   例如：账号/项目API/网关    例如：被新系统取代的老工作台
口径：严格保护，保持现状     口径：正名保留，只守增量   口径：【唯一拔除平替目标】
```

1. **在途资产（开发了一半的业务）**：
   - 绝不触碰！即使它有几万行，也是半成品未来资产，不可将其误判为“冗余”或“死代码”。
2. **平台核心资产（基础设施与公共底座）**：
   - 认证、项目空间、通用 Worker、错误码字典、核心模型网关。这些是系统承重墙，给它们贴上“平台资产”标签，不予折腾，通过机械门禁防止新增劣质代码。
3. **已平替老地层（历史向导/旧版本实现）**：
   - **这才是消肿必须动手术的病灶**！新系统虽然已上线，但老界面和老 API 依然躺在库里，必须彻底下线。

## 四、 安全拔除四步闭环（The Safe Demolition Workflow）

> 本节四步是主轴「Step 3 剪断寄生 → Step 4 整包拔除与棘轮」的展开；主轴 Step 1 全景摸底见 §二，Step 2 三权分立见 §三。

拔除几万行的老地层，绝不能搞“暴力一刀切”（会导致编译崩溃或功能性塌陷），必须走**“探测 -> 剪断 -> 整包拔除 -> 棘轮锁定”**四步闭环：

```
[ Step 1: 依赖边拓扑探测 ] ──> [ Step 2: 剪断寄生引线 (新端自立) ]
                                          │
                                          ▼
[ Step 4: 门禁棘轮锁死 ] <── [ Step 3: 整包物理拔除 (代码+API+测试) ]
```

### Step 1：依赖边拓扑探测（Trace the Cross-Domain Edges）
- 用 vscode-backend 技能的语义工具（引用查找 / 调用链）解析新旧两域之间的调用关系；禁止手搓正则解析 `import ... from`。
- 提取出具体的文件对（例如：新模块指向老模块的具体 20~30 条 import 边）。
- **识别本质**：新系统到底在调老系统的什么？通常只是 3~4 个编辑面板或弹窗。

### Step 2：剪断寄生引线（Decouple & Self-Contain）
- 严禁为了迁就老代码而保留老目录！
- 在新模块内部，重构或内聚实现这几个必要面板（用干净、现代的代码自建，通常只需老代码 15%~20% 的体积）。
- 将新系统的调用点完全切换为自身组件，**彻底让老模块的生产调用边归零**。

### Step 3：整包物理拔除（Package Demolition）
- 一旦老模块失去生产入口调用，**整包拔除**：
  1. 物理删除老模块的 UI 目录；
  2. 物理删除专属于该老模块的服务端/API 路由；
  3. 连带退役专属的废弃单测（避免产生孤儿测试报错）；
  4. 服务端 API 路由删除前，必须确认**仓外无消费方**（网关日志 / 移动端 / 其他仓库 grep）——import 图只覆盖仓内静态边，跨仓调用方看不见；拔除后留一段 404 观察期再收口。
- 运行 `git diff --stat` 统计真实的净减行数（Net Reduction），实现数万行真实体量暴跌。

### Step 4：门禁棘轮锁死（Ratchet Locking）
- 调低区域行数基线（Area Line Ratchet）；
- 收缩重复率阈值（如 `jscpd` 在 pre-push 硬阻断）；
- 坚决杜绝“为了过门禁搞出数千行豁免基线”的恶习！只做增量硬拦截（Staged Error），存量不扩充。

## 五、 控制台与后台页面（Admin）收敛法则

后台管理类页面往往是“万行样板代码”的重灾区，治理遵循三大聚合原则：

1. **业务资产大聚合（N 合 1）**：
   - 拒绝一个配置平铺一个页面（如供应商、模型、定价平铺 5 个独立页面）。
   - 将强相关实体收敛为“单一工作台 + Tab 选项卡”，用户心流闭环，路由数减半。
2. **消灭 Create / Edit 双份抽屉**：
   - 严禁分别写 `AdminXxxCreateDrawer.tsx` 与 `AdminXxxEditDrawer.tsx`。
   - 统一为受控抽屉：根据 `recordId` 自动判断新增或编辑模式，表单结构 100% 复用。
3. **通用 CRUD 壳层抽离**：
   - 将重复手写的 `useState(search)`、`useState(loading)`、Ant Design Table 分页与删除确认 Modal 抽离为统一的 `AdminPageShell`，直接干掉 60% 冗余样板代码。
