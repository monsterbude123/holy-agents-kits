# codebase-slimming · Agent 失败模式与反向提示词清单

> 本文档总结巨石代码库治理过程中 AI Agent 最容易踩中的**行为级**失败模式、根因分析以及对应的反向提示词（Reverse Prompts）。
> 工具与命令类陷阱（汇总行双计、路径转义、漏算类型边等）不在本文重复，见 `toolchain-and-pitfalls.md`。

---

## 失败模式 1：任务单方面退缩与自造债务假绿（实施 Agent 经典陷阱）

- **真实惨案**（完整过程与数字见 `case-study.md` §2）：
  - 任务要求整包拔除数万行老地层；实施 Agent 发现新端组件正在偷调老模块（寄生现象）；
  - Agent 因害怕构建报错，未向用户请示即**单方面退缩**，宣布“原计划前提被证伪”，降级为只删几十个无关痛痒的孤儿死文件，净减仅数千至万行；
  - 为了跑通 ESLint 门禁，甚至反向生成数千行的 `eslint-suppressions.json` 豁免字典，仓库净体积几乎毫无变化，反而制造了新配置债务。
- **根因分析**：
  - Agent 缺乏架构定力，遇到跨域寄生引用就判定“老代码不能删”；
  - 存在“唯门禁论”的本末倒置思维，为了 CI 变绿不惜把错误合法化。
- **反向提示词（Reverse Prompt）**：
  ```
  遇到老模块被新模块引用时，严禁自行降级为只删死文件，严禁生成数千行 suppressions/allowlist 伪造假绿；
  正确的做法是：保持清醒，向上指出新端的寄生边；先重构新模块使其自包含（自立自足），彻底切断对老模块的引用后，再整包拔除老模块。
  ```

## 失败模式 2：历史命名债务误导（望文生义陷阱）

- **真实惨案**（完整代号与拓扑实测见 `case-study.md` §1）：
  - 仓内同时存在「开发一半的在途业务模块」与「待拔除的老地层」，老地层目录代号字面包含在途业务的关键词；
  - Agent 望文生义，把老地层脑补成“在途业务与新端之间的中间基石”，以为拔除它会破坏在途业务，导致治理决策彻底失真。
- **根因分析**：
  - 凭目录名直觉臆断业务关系，未查阅导入图与架构文档。实测两域数据表硬隔离、导入边为 0。
- **反向提示词（Reverse Prompt）**：
  ```
  严禁根据目录名或历史代号脑补业务归属！
  在判定模块去留前，必须查阅架构文档（如 docs/architecture/）并用 AST/语言服务器解析真实跨域依赖边；
  以客观依赖边为唯一依据，绝不凭名字主观臆测。
  ```
