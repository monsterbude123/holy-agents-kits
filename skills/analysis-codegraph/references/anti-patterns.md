## §3 反模式 7 姿势

| # | 姿势 | 信号（脑子里出现这句 = 已中招） | 强制动作 |
|---|---|---|---|
| 1 | **凭记忆编** | 「I remember…」「上次看过」 | `explore` |
| 2 | **grep 当探针** | `Grep pattern=...` 然后直接 `Edit` | `explore` |
| 3 | **Read 整个文件** | 500+ 行全量读 | 用 `explore` 返回的逐字源码，或 `Read` 指定 offset / limit |
| 4 | **跳过 blast radius** | 改完炸一片才发现漏了调用方 | 每次 `Edit` 前 `explore`，读 Blast radius 段 |
| 5 | **改完直接 commit** | 没确认影响面就提交 | 收尾自检 |
| 6 | **ceremonial-call** | 「turn1 调过，后面 skip」 | MUST-ORIGIN-1 / 2（`references/trigger-matrix.md` §0） |
| 7 | **边界泄漏** | 「我就 import 一个常量，有什么关系」 | 见下方详解 |

> **姿势 6 是「形式主义」的学名**：工具调过了，分析却降级了。补救不是再劝一次，是**补调**。

### 姿势 7 详解：模块边界泄漏

> 姿势 1-6 管的是「怎么查」，姿势 7 管的是**「查到了之后敢不敢动」**——
> 前 6 条让你看见依赖图，第 7 条要求你在改之前**读懂这张图的边界含义**。

**信号**：`const` / 类型 / 纯数据这类「无副作用、显然安全」的共享物，让你想省事直接从重模块 import——
例如从服务端专用模块、数据库客户端或带原生依赖的包里取一个常量 / 类型。

**为什么「就一个常量」不成立**：`explore` 的 `Relationships` 段是**传递闭包**。
客户端组件 import 一个服务端模块，浏览器 bundle 会连带编译它的全部依赖
（ORM、日志、`node:fs` 等），编译失败后**整个站点的路由都可能 500**，与那个路由自身无关。

**强制动作**：

1. 改之前先看 `explore` 的 `Relationships`：这条引用链的**另一端是客户端 / 边缘运行时吗**？
   是 → 先把共享物抽成 **client-safe 纯模块**（零副作用 / 纯数据 / 纯类型守卫）。
2. 原处改成 import + **re-export**，既有引用路径一行不改。
3. 加一条**源码断言**回归测试钉住边界（如断言源码中不出现那条 import 路径），
   否则下一个 agent 会「顺手改回去」。

**判别口诀**：`explore` 能查到边界，但**查不到它合不合法**——合法性要靠「另一端跑在哪个运行时」这条人工判断，工具替代不了。

## 收尾自检（每次代码调查 / 编码任务结束时必答）

> **不要数 codegraph 调了几次。** `codegraph_explore` 的设计是「一次回答大部分问题」，
> 1 次是正常形态。**计数不是病，用 grep 顶替「发现」才是病。**

### 把本次所有 `grep` / `ls` / `find` 逐条分类

| 类型 | 判据 | 结论 |
|---|---|---|
| **验证型** | 你已经知道确切文件或符号，只是去核对一个具体细节 | ✅ Grep / Read 正确 |
| **发现型** | 你不知道它在哪，在搜「这个符号还出现在哪 / 谁调用它 / 谁写入了它 / 改了会怎样」 | ❌ **漏掉的补招**——这类问题正是 Blast radius / Relationships 段 |

**分界线（可机械判定）**：

- 搜的**是代码符号**（函数 / 类 / 组件 / 类型 / 变量 / 导出）出现在哪 → **发现型 = 漏招**
  理由：`Relationships` 段直接给 references + callers + file:line，比 grep 全得多。
- 搜的**是字符串字面量**（配置 key / i18n key / 环境变量名 / URL / schema 字段名） → **验证型 = Grep 正确**
  理由：这类东西不在符号图里，codegraph 答不了。

**两问**（答案写进给用户的汇报，不是心里过一遍）：

1. 本次 `grep` / `ls` / `find` 共几次？其中**发现型几次**？
2. **发现型 > 0 = 本次有漏招** → 补调 `codegraph_explore` 后再交，并把补调写进汇报。

> 注意：`Read` 一个刚在 explore 返回体里见过的文件是**正常的**（核对细节），不计入发现型。
> **只有「我得去找」才要放大招。**

### 「补招」的触发条件（可观测，不靠感觉）

**准备发起 grep / ls / find，且问题里含下面任一措辞——那就是一次漏掉的补招：**

> **「……在哪」「谁调用了它」「谁写入了它」「还有谁在用」「改了它会影响谁」**

这五个措辞就是 Blast radius 段与 Relationships 段的标准答案。用 grep 回答它们，等于**用手电筒去找地图上已经画好的路**。

**反例（这两个不触发补招）**：

- 「`NEXT_PUBLIC_FOO` 这个环境变量名在代码里哪出现过」→ 字符串字面量，Grep 正确
- 「我刚读的这个函数第 120 行在干嘛」→ 已知位置，Read 正确

## §3.1 降级前三问（想转 Grep / Read 之前逐条自问）

任一为真 = **不许降级**，回到 `explore`：

1. 我要搜的**是代码符号**（函数 / 类 / 组件 / 类型 / 导出）吗？→ 是则用 `explore`。
2. 我是**因为上一次 explore「看起来够了」**而顺手转 Grep 吗？→ 是则停下，补调。
3. 我是**因为 `maxFiles=12` 截断了**才转 Grep 吗？→ 是则**调高 `maxFiles` 重调**。

## §3.2 「我记得…」自检（MUST-ORIGIN-4 的操作化）

以下场景**不允许**靠记忆推进，必须先 `explore`：

- 用户报错文案模糊，不确定涉及哪些模块
- 「记得」某函数在哪，但记不清它的全部调用方
- 距上次 explore 已跨过一个方向（从前端跳到 worker / 从 auth 跳到 billing）
- 要改的文件超过 3 个，或跨了 2 个以上目录

不确定就调。**「不确定」本身就够了，不需要先找到一个具体理由。**
