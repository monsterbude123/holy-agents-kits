# 温度值(Temperature)

> 历史失败累积指数：把「用户在该领域反复纠正」变成可计算的严重程度信号。
> 本文原为 emotional-neutralizer.md §2.5，独立成篇。

---

## 为什么温度值必保留

> **V2.2 反模式 #1 修正**:之前以为"情绪 = 噪声,全剥 = 优化"。**错的。** 情绪载荷同时承载两类信号:
> 1. **噪声**(情绪词本身) → 必剥
> 2. **严重程度**(情绪强度) → **必保留为温度值**
>
> **温度值的本质**:不是"用户情绪强度",而是"**该诉求域的历史失败累积指数**"。一个用户从未爆发过的领域 = 低温(可能是首次踩坑);一个用户反复疲于纠正的领域 = 高温(规则冲突多,agent 必重点自审视)。

### 2.5.1 温度值计算公式

```
T = base_intensity × accumulation_factor × history_weight

其中:
  base_intensity    = 当前发言的情绪载荷密度 (0-1, see §3 Step 1 emotion_score)
  accumulation_factor = 同领域历史爆发次数因子
                       ├─ 0 次 → 1.0 (首次,无历史)
                       ├─ 1-2 次 → 1.5 (开始累积)
                       ├─ 3-5 次 → 2.5 (用户疲于纠正)
                       └─ ≥ 6 次 → 3.5 + 0.5×(次数-5)  (不封顶：封顶时
                          T 上限只有 3.5，🔥 红区与 🚨 危机永远触发不了)
  history_weight    = 时间衰减
                       ├─ 最近 1 周爆发 → 1.0
                       ├─ 1 周~1 月前 → 0.8
                       ├─ 1~3 月前 → 0.5
                       └─ > 3 月前 → 0.3

T 取值范围: 0.0 起无理论上限。emotion_score≤1、hw≤1 时靠 accumulation_factor 增长；> 6 进 🔥 红区，> 10 进 🚨 危机。
```

### 2.5.2 温度 → 关注度映射

| T 区间 | 关注度等级 | agent 自检动作 | 修复策略 |
|--------|-----------|---------------|---------|
| **0.0 - 0.3** | 🟢 冷区 | 无额外动作 | 按常规流程 |
| **0.3 - 1.0** | 🟡 微温 | 标记"待观察" | 写入 self-improving-agent LEARNINGS |
| **1.0 - 3.0** | 🟠 热区 | 触发"规则审视":检查当前诉求域是否违反已有铁律 | 实时回查 §1 三大铁律 |
| **3.0 - 6.0** | 🔴 灼热 | 触发"根因诊断":agent 必须先输出"本次可能违反哪些既有规则"的清单,再行动 | 强制先核对铁律再执行 |
| **6.0 - 10.0** | 🔥 红区 | 触发"协议变更建议":agent 必须建议用户"该诉求域规则需要重写/拆分/合并" | 不直接修复,先汇报用户 |
| **> 10.0** | 🚨 危机 | 🛑 阻塞:agent 必须停止一切动作,先与用户对齐"为什么该领域已成规则冲突黑盒" | 升级到顶层决策 |

### 2.5.3 为什么温度值必保留?

```
❌ V2.2 错误做法(完全中性化):
  "上一步结果与预期不符,请定位根因。"
  agent 收到 → 照常执行
  agent 不知道:这个诉求域用户已经纠正过 N 次 → 必重点自检

✅ V2.2.1 正确做法(中性 + 温度):
  "上一步结果与预期不符,请定位根因。[温度=6.2 🔥红区,历史爆发 5 次]"
  agent 收到 → 触发"根因诊断"前置
  agent 必须先输出: "本次诉求域相关规则冲突清单: ..."
  再行动 → 避免重蹈覆辙
```

### 2.5.4 温度值的来源(数据采集点)

```
MUST 采集:
  1. 当前发言的 emotion_score (§3 Step 1)
  2. 同领域历史爆发次数(查**项目内** .learnings/ERRORS.md 同 tag；没有就按 0 计，别去全局库找)
  3. 同领域最近一次爆发距今的时间(查**项目内** .learnings/LEARNINGS.md 时间戳)

SHOULD 采集:
  4. 同领域是否有规则冲突记录(查 rules + SKILL.md frontmatter 矛盾)
  5. agent 历史上在该领域的失败率(查 completion-report 历史)

实现位置:
  - 输入端:项目内 .learnings/ERRORS.md 同 tag 计数（范围同去重检查：只项目内，不碰全局库）
  - 中性化器:本协议 §3 Step 1 计算 base_intensity
  - 合并:§3 Step 5 标注 temperature + history_count + last_incident
```

### 2.5.5 与 emotion_score 的区别

| 维度 | emotion_score | temperature |
|------|---------------------|---------------------|
| **本质** | 当前发言的情绪载荷 | 历史失败累积指数 |
| **范围** | 0-1 | 0-10 (理论无上限) |
| **决定因素** | 语气词/叹号/攻击词 | 同领域历史爆发次数 × 时间衰减 |
| **用途** | 触发中性化动作 | 触发 agent 自检动作 |
| **数据源** | 当前发言 | .learnings/ + 历史 |
| **稳定性** | 单次发言瞬时值 | 跨会话累积值 |

**关键区别**:emotion_score 高 = 单次激烈(可能只是用户当下心情差);temperature 高 = 该领域系统性问题(规则冲突已固化,必打破)。
