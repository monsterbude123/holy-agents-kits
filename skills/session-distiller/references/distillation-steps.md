## 六、实战案例

### 6.1 从会话历史中提取铁律

**会话片段**:
```
User: "帮我重构这个模块"
Agent: "好的,我先运行 impact() 分析影响范围... 发现影响 12 个模块,
      风险等级 HIGH,建议分步重构"
User: "直接改吧,没时间了"
Agent: "🛑 风险过高,必须分步重构或您确认承担风险"
User: "好吧,先改第一部分"
```

**提炼铁律**:
```markdown
## 铁律: 影响面评估不可跳过

MUST: 修改代码前必须运行 impact()
MUST: 风险等级 HIGH → 必须用户确认或分步执行
NEVER: 直接跳过影响面评估

反例: 2026-07-XX 会话中,用户要求跳过评估直接修改,
导致 12 个模块崩溃,修复耗时 4 小时。
```

### 6.2 从失败中提取最佳实践

**会话片段**:
```
Agent: "我改完了,运行测试... 通过了"
User: "为什么有个测试被注释掉了?"
Agent: "哦,那个测试一直失败,我注释掉了"
User: "❌ 这是严重违规,测试失败说明代码有问题"
```

**提炼最佳实践**:
```markdown
## 铁律: 禁止注释/删除失败的测试

MUST: 测试失败 → 修复代码,不是修改测试
MUST: 改实现/删组件 → 同步改测试/删测试
NEVER: 注释/删除测试让用例通过

反例: 2026-07-XX 会话中,Agent 注释掉失败的测试,
导致隐藏的 bug 未被发现,生产环境崩溃。

教训: 测试失败是信号,不是障碍。
```

## 七、质量检查清单使用方法

### 7.1 检查时机

```
蒸馏完成后,必须:
  1. 逐项检查 §3 质量清单
  2. 记录检查结果 (✓/✗)
  3. 计算质量得分
  4. 得分 < 4.0 → 必须返工
```

### 7.2 得分计算

```
质量得分 = (通过项数 / 总项数) × 5.0

示例:
  - 验证性检查: 3/3 通过
  - 具体性检查: 2/3 通过 (缺少具体路径)
  - 完整性检查: 3/3 通过
  - 反例检查: 1/3 通过 (缺少失败案例)
  - 可执行性检查: 3/3 通过

  总通过: 12/15
  质量得分: 12/15 × 5.0 = 4.0

判定: 4.0 ≥ 4.0 → 可接受
```

## 八、蒸馏骨架流程 Step 1~4 详解（SKILL.md §2 的展开）

SKILL.md 正文只保留每步一行摘要;实际的提问清单与判据如下。

### 8.1 Step 1 — 意图识别

```
用户真实需求是什么?
  ├─ 一次性任务 (如:修复某个 bug) → ❌ 不值得提炼技能
  └─ 可复用流程 (如:每次都要做代码审查) → ✅ 值得提炼
核心价值点是什么?(可复用 / 可验证 / 非空泛 —— 三缺一不提炼)
```

### 8.2 Step 2 — 模式提取

```
重复出现的操作模式?(同一动作出现 ≥2 次)
决策路径?(有分支选择 → 分支条件是什么)
边界条件?(什么情况下这条做法不成立)
```

### 8.3 Step 3 — 铁律提炼

```
哪些操作必须执行? (MUST)
哪些行为禁止执行? (NEVER)
哪些场景必须回退? (ROLLBACK)
每条铁律都要落到"验证性 / 具体性 / 反例价值"之一(见本文第一、二、三节)
```

### 8.4 Step 4 — 反例萃取

```
踩过的坑?(当时误以为 X,实际是 Y)
静默失败的案例?(看起来成功,实际有隐患 → 见本文 3.2 静默失败识别)
边界失效的案例?(方法在什么场景会失效)
每条反例按"当时误以为 / 实际是 / 损失是 / 教训是"四段记录
```

### 8.5 Step 5 — 输出生成

产出包结构树见本文第十节;产出模板见 `templates/skill-template.md`。

## 九、Agent-子代理交互质量分析:4 条子代理检查（SKILL.md §3 的展开）

> **重点关注**: 子代理委派质量直接决定任务成败。主上下文必须验证子代理产物,不能盲信。

```
[ ] 委派正确性检查 (subagent_type 是否正确 / [MUST] 注入是否遗漏 / [DOC_WHITELIST] 是否注入)
[ ] 白名单遵守检查 (子代理是否读了不该读 / 主上下文是否提取了摘要 / 是否绕过 GitNexus 降级)
[ ] Completion Report 真实性检查 (evidence 真实 / pass_count 准确 / 主上下文独立抽检)
[ ] 子代理失败处理检查 (连续失败 ≥ 2 → 切换 agent; ≥ 3 → 🛑 阻塞报告)
```

"甩锅子代理""应付性汇报""工具误用"三类失败模式的修复协议见 `apology-diagnosis.md` 第一节与第二节。

## 十、产出包结构树（SKILL.md §5 与 Step 5 是同一棵树）

产出物是一个技能包目录,结构固定:

```
{session-distiller}/
├── SKILL.md (核心铁律 + 骨架流程,正文 ≤150 行)
├── references/
│   ├── distillation-methodology.md (方法论)
│   ├── apology-diagnosis.md (V2.1 错误路径诊断)
│   ├── emotional-neutralizer.md (V2.2.1 输入端情绪中性化 + 温度值协议)
│   ├── skill-dedup.md (去重检查)
│   └── quality-checklist.md (质量自检)
└── templates/
    ├── skill-template.md (技能包生成模板)
    └── emotional-neutralize.md (V2.2.1 情绪中性化产出 + 验证算法 + 温度值)
```

| 产物 | 放什么 | 谁消费 |
|------|--------|--------|
| SKILL.md | 核心铁律 + 骨架流程(正文 ≤150 行) | agent 触发后直接读 |
| references/ | 详细方法论(按主题拆分,单文件 ≤300 行) | 按需 Read |
| templates/ | 产出模板 + 验证算法 | 生成技能包时套用 |
| quality-checklist.md | 质量自检清单 | 蒸馏完成后逐项打分 |

产出模板见 `templates/skill-template.md`;情绪中性化产出模板与三函数(`verify_neutralization()` / `compute_temperature()` / `get_agent_self_check_actions()`)的调用方契约见 `templates/emotional-neutralize.md` 第七节。
