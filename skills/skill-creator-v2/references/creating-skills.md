# 新建技能：从立边界到写测试用例

对应骨架流程的 ① 立边界 → ② 起骨架 → ③ 填核心。

---

## 1 立边界（Capture Intent）

当前对话里往往已经有用户想要的流程（例如他说「把这套流程固化成 skill」）。
**先从对话历史里提取**：用过的工具、步骤顺序、用户做过的纠正、观察到的输入输出格式。
用户只需要补缺口，确认后再往下走。

要问清楚四件事：

1. 这个技能要让 agent **能做什么**？
2. **什么时候该触发**？（用户会怎么说这件事）
3. 期望的**输出格式**是什么？
4. 要不要建测试用例？输出客观可验证的技能（文件转换、数据抽取、代码生成、固定流程）
   值得建；输出主观的技能（写作风格、审美）通常不需要。按技能类型给建议，**由用户定**。

**边界**：明确写出这个技能**不**做什么。边界不清的技能会到处抢触发，最后谁都不可靠。

---

## 2 访谈与调研

主动追问边界情况、输入输出格式、样例文件、成功判据、依赖。
**访谈没做完不要写测试用例**——用例是从约束里长出来的，不是拍脑袋编的。

调研可以并行：查文档、找现成的相似技能、看最佳实践。
能用子代理就并行，否则内联做。带着结论来，别把调研成本转嫁给用户。

---

## 3 起骨架

```bash
python .agents/skills/skill-creator/scripts/scaffold_skill.py skills <name> --description "一句话说明"
```

生成的是三段式空骨架（骨架流程 / 核心逻辑 / 核心循环）+ `references/` + `scripts/`。
骨架自带行数约束，天然符合 ≤ 150 行。

---

## 4 填核心

按 `references/structure.md` 的三段式填。每一段只写**判断依据**：

- **骨架流程**：步骤 + 每步的输入产出。步骤数控制在 3~7 步，步骤之间是严格顺序还是可并行？
- **核心逻辑**：什么情况下走 A 路、什么情况下走 B 路、什么情况下直接报错不做兜底。
  没有分支就别硬写分支。
- **核心循环**：迭代时每圈做什么、拿什么当退出条件。一次性流程就别硬写循环。

### description 怎么写

它是唯一的触发依据，同时要写清「做什么」和「什么时候用」，并带上用户的真实说法：

```yaml
description: 通过 ai_gateway 网关按能力类目调用模型服务——文档解析（PDF 转 Markdown）、
  语音转写、文本向量化、对话补全。调用方只说「把这个 pdf 转成 md」即可，不必关心模型名。
  当任务涉及「PDF 转 Markdown」「OCR」「语音转文字」「向量化」「列出网关模型」时加载。
  触发词：网关、gateway、pdf转md、文档解析、ASR、转录、embedding、LLM 调用。
```

**反例**：只写「文档处理工具」。没有场景、没有触发词，等于没写。

---

## 5 写测试用例

写完草稿后，准备 2~3 个**真实用户会说的话**当测试提示。
先跟用户确认：「这几个用例我打算这么跑，你看行不行，要不要补？」
然后再跑。

用例存到 `evals/evals.json`。**先只写提示词，断言下一轮再补**：

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的真实任务描述",
      "expected_output": "期望结果的描述",
      "files": []
    }
  ]
}
```

完整 schema（含 `assertions` 字段）见 `references/schemas.md`。
怎么跑、怎么评分见 `references/evaluating.md`。
