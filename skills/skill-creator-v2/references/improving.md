# 从反馈到改进

对应骨架流程的 ⑥ → ③ 的回环。这是整套方法里最核心的一步。

---

## 1 怎么想改进

1. **从反馈里泛化。** 这批技能将来要被用无数次，你现在只在几个样例上反复迭代——这正是为了快。
   如果技能只在这些样例上好用，它就没用。要改就改出**通法**：
   遇到顽固问题时，换个比喻、换种工作方式，往往比加一条限制有效得多。

2. **保持提示词精简。** 删掉没在产生价值的部分。
   **先读 transcript，再看最终产出**——如果技能让模型在无用功上浪费时间，
   砍掉制造这些时间的那几行，然后看会发生什么。

3. **讲清为什么。** 现在的模型很聪明，给一个好支架它能处理你没写到的情况。
   用户反馈很简短甚至带着情绪时，先理解他真正想要什么、真正写了什么，再把这个理解写进指令。
   满屏 `ALWAYS` / `NEVER` 是危险信号——能讲道理就别立规矩。

4. **找出重复劳动。** 读 transcript，如果多个子代理各自写了相似的辅助脚本、
   或走了同一个多步流程，那就是明确信号：**这段该固化成 `scripts/`**。
   写一次，放进 `scripts/`，并在 SKILL.md 里指明用它。
   这样每次调用都省掉一次重新发明。

这一步不急。写一版草稿，再**用新鲜的眼睛重读一遍**并改进。
先搞清楚用户真正想要什么、需要什么，再动手。

---

## 2 迭代循环

改完之后：

1. 把改进应用到技能上。
2. **重跑全部用例**到新的 `iteration-<N+1>/`，**基线也要重跑**。
   新建技能的基线永远是 `without_skill`（完全不给技能），跨轮不变；
   改造已有技能的基线由你判断：用用户最初拿来的版本，还是上一轮。
3. 带上 `--previous-workspace <上一轮目录>` 重新出评审视图。
4. 等用户看完并告诉你完成。
5. 读新反馈，再改，重复。

**什么时候停**：

- 用户说满意了
- 反馈全是空的（都挺好）
- 再改也没有实质进展

---

## 3 盲测对比（可选）

需要更严格地回答「新版本到底是不是更好」时用。
读 `agents/comparator.md` 与 `agents/analyzer.md`。
做法：把两份输出交给一个不知道哪份是哪份的独立代理，让它判优劣，再分析赢的原因。

这个流程需要子代理，多数用户用不上——**人工评审回路通常已经够了**。
