# 技能结构与写作规范

写技能前先读这份。它定义**一个技能长什么样**、每个字段怎么填、正文怎么写。

---

## 1 目录布局

```
<skill-name>/
├── SKILL.md (必需)
│   ├── YAML frontmatter (name, description 必需)
│   └── Markdown 正文
├── scripts/       可选 —— 固化的确定性流程
├── references/    可选 —— 按需加载的细节文档
└── assets/        可选 —— 输出用的模板、图标、字体
```

| 目录 | 什么时候用 | 约束 |
|---|---|---|
| `scripts/` | 有「每次都要重写一遍」的代码 | 只依赖标准库；有 `--help`；stdout 是结果、stderr 是过程日志 |
| `references/` | 协议表、错误码、示例集、长清单 | 单文件 ≤ 300 行；超过继续按主题拆 |
| `assets/` | 要被复制进产物的静态文件 | 不在里面写说明文档 |

**判据**：内容会被**每次触发**都读 → 放正文；只在**特定分支**才读 → 放 references；
**根本不需要读**、只需要执行 → 放 scripts。

## 2 frontmatter schema

```yaml
---
name: my-skill              # 必需，kebab-case，≤ 64 字符，必须等于目录名
description: ...            # 必需，≤ 1024 字符，不含尖括号
license: ...                # 可选
allowed-tools: ...          # 可选
metadata: ...               # 可选
compatibility: ...          # 可选，≤ 500 字符
---
```

| 键 | 必填 | 规则 |
|---|---|---|
| `name` | 是 | `^[a-z0-9]+(-[a-z0-9]+)*$`；≤ 64 字符；**必须等于目录名** |
| `description` | 是 | ≤ 1024 字符；不能含 `<` `>`；至少写清「做什么 + 何时用」 |
| `license` | 否 | SPDX 标识或自由文本 |
| `allowed-tools` | 否 | 限制技能可用的工具 |
| `metadata` | 否 | 任意嵌套字段，校验器不检查其内部 |
| `compatibility` | 否 | 依赖说明，≤ 500 字符 |

**frontmatter 之外的顶层键一律判错。** 校验规则由 `scripts/skill_schema.py` 统一实现，
改规则只改那一个文件，不要在别处重复实现。

## 3 正文写什么

### 3.1 三段式骨架

新技能统一按这三段组织，agent 一眼能定位：

| 段落 | 回答什么 |
|---|---|
| **骨架流程** | 分几步做？每步的输入与产出是什么？ |
| **核心逻辑** | 为什么这么做？什么情况下换一条路？ |
| **核心循环** | 迭代时每一圈做什么？什么条件算完成？ |

步骤粒度：**每步一行**。一行说清「做什么 + 怎么算完成」即可；命令、参数、工具名不进步骤行，
集中在正文「脚本」段或 `scripts/`，步骤行里出现具体命令就是越位。

### 3.2 行数预算

| 文件 | 上限 | 超了怎么办 |
|---|---|---|
| SKILL.md 正文 | 150 行 | 抽到 `references/`，原处留指针 |
| `references/*.md` | 300 行 | 按主题继续拆 |
| `references/` 单文件 | 无数量上限 | 按主题组织，不要平铺 |

SKILL.md 正文 = frontmatter 之后的全部行。

### 3.3 指针怎么写

抽走内容后，原处**必须**留下一行指向新文件，指明**什么时候读它**：

> 完整内容已抽取到 `references/gateway-api.md`（原章节：协议细节）。排查具体错误码时再读该文件。

只写「详见某某」不够——模型不知道什么时候该去读，细节就等于丢了。

### 3.4 写法偏好

- **每条 ≤ 2 行**：结论一句 + 理由（或指针）一句；写满三行就该外迁或删。
- **同一判断只写一次**：流程写动作、逻辑写判断、退出条件只写判据清单；同一条规则出现第二遍就是注水。
- **命令不进散文**：单条命令与参数示例集中在「脚本」段，正文只提脚本名与用途。
- 用**祈使句**写指令，而不是描述状态。
- 讲清**为什么**，而不是堆 `MUST` / `绝对不要`。模型理解理由后能自己处理没写到的情况；
  硬约束只能覆盖被写到的情况。
- 语气要匹配用户的熟练度。用户说「帮我把这个 pdf 转成 md」，就回「好，我用解析模型转」，
  不要解释什么是 OCR。
- 输出格式用模板钉死：

```markdown
## 报告结构
始终使用这个模板：
# [标题]
## 摘要
## 关键发现
## 建议
```

- 举例要具体。抽象例子帮不了模型定位，真实例子能。

### 3.5 安全底线

技能内容不得包含恶意代码、漏洞利用，或任何削弱系统安全的东西；
技能的实际行为不得超出它描述的意图。角色扮演类技能没问题。

## 4 命名

| 对象 | 规则 | 例子 |
|---|---|---|
| 目录名 | 与 `name` 完全一致 | `work-with-ai-gateway` |
| `name` | kebab-case，单个连字符 | `parse-to-md` |
| `references/` 文件 | 小写 kebab-case + `.md` | `gateway-api.md` |
| `scripts/` 文件 | 小写 kebab-case + `.py` | `validate_skill.py` |

**目录名与 `name` 不一致是最常见的低级错误**，校验器会直接判错。
