# 复核协议 —— 不采信执行方自检

规则层改动天然「看起来都对」：格式统一了、行数降了、门禁全绿了。
但**格式统一和语义保真是两件事**，自动化改写尤其容易在没人看的地方丢东西。

---

## 一、三向语义保真校验（核心）

对每个被改写的规则文件做三组比对，全部机械执行：

```
方向 A（旧 → 新）：旧文件里每一个「规则文本单元」，必须在新文件里找得到
                   → 失败 = 丢失了内容（把规则改没了 / 删了没留指针）
方向 B（新 → 旧）：新文件里每一个「规则行」，必须能在旧文件找到对应原文
                   → 失败 = 杜撰（凭空加的规则 / 编造的出处）
方向 C（非规则内容）：表格 / 代码围栏 / 目录树 / 指针表的**行数与内容**不变
                   → 失败 = 误伤（改格式时手滑碰了不该碰的）
```

### 怎么做

1. 从 HEAD 取出改写前的版本（`git show HEAD:<path>`）
2. **归一化**再比对，否则格式差异会淹没一切：
   - 剥掉模板尾缀（`| 出处: ... | 候选下沉: ...`）
   - 剥掉来源括注（`（...来源...）`、`| 出处: ... |`）
   - 归一空白（全角/半角、连续空格、markdown 转义）
3. 剩下的就是「规则文本单元」，逐个做子串 / 集合比对

### 铁律

- **归一化只许剥不许改**。归一化脚本本身也是代码，也要用 ASCII 校验输出（中文易乱码，
  用 `grep -c` / `od -c` 而不是肉眼比对）
- **子串比对必须逐条人工定性**。自动比对只负责「标出来」，判「是噪声还是缺陷」必须人做。
  典型的可解释噪声：跨行条目被合并后计数对不上、段落被升格成规则行、另一会话的并行新增。
- **不确定就当缺陷**。宁可多查一轮，不可放过一处真丢失 —— 规则丢失是静默的，
  几个月后没人知道原来有过这条

## 二、并行基准差异的处理

复核期间**很可能有别的会话在同时改同一个仓**。判别法：

```
校验器说「杜撰」，但 git HEAD 里没有 →
  1. 查工作区里是否真有对应改动（git status / 该文件的其它新增）
  2. 查经验账本里有没有新条目（LRN / ERR / FEAT 编号与时间戳对得上）
  3. 对得上 → 这是**基准差异**，不是本轮缺陷，人工定性后放行
  4. 对不上 → 才是真杜撰
```

**推论：复核必须记录基线快照时刻**。跨了会话再复跑，结论不可比。

## 三、门禁回归

改完规则文件，**所有相关门禁都要重跑一遍**，不能只跑新增的：

```bash
for g in scripts/gates/*.sh; do
  [ "$(basename "$g")" = "check-rules-stale.sh" ] && continue
  bash "$g" >/dev/null 2>&1; echo "$g exit=$?"
done
```

- **规则文件本身有行数预算 → 改写可能触发体积门禁**，必须重跑
- **任一 gate 处于违规态（exit != 0）必须如实上报**，不能因为「这是已知问题」就不说
- 已知违规要在报告里写清处置选项（接线 / 登记豁免），交人拍板

## 四、死引用扫描

规则文件里的路径引用会随重排、改名、删除而腐烂。

```bash
bash scripts/gates/check-rules-stale.sh          # 真实扫描
bash scripts/gates/check-rules-stale.sh --selftest # 自测（样例含 1 条死引用，期望 exit 1）
```

扫描结果**必须逐条人工分类**，实测一次会出现这几类：

| 类别 | 判据 | 是否要修 |
| --- | --- | --- |
| 真死引用 | 路径确实不在磁盘上、也不在 git 里 | 要修 |
| 外来约定 | 同行显式声明「本仓不存在」「外部约定」「若项目有」 | 不修 |
| 示例 / 教学 | 同行含「例如」「e.g.」 | 不修 |
| 他 agent 配置 | `.trae/` `.claude/` `.codex/` 等本仓预期不存在的路径 | 不修 |

**重排前后的扫描结果应当逐条一致** —— 若变了，说明重排碰了路径引用，立刻查。

### 扫描器自身的坑

- **解析基准 ≠ 样例落点**：`--selftest` 时样例写在临时目录，但真实存在的路径必须**仍以仓库根为基准**解析。
  两者搞混 → 自测样例里会混进「误报真实文件」→ 自测 FAIL 但代码是对的
- **过滤规则要显式**：通配（`*` `?`）、占位（`<>` `{}` `$`）、URL（含 `://`）、
  家目录（`~`）、CLI 选项（含 `--`）、带空格的代码片段 → 都不是路径型 token
- **用后即删**：样例目录、临时清单、mock 桩，全部清干净再收工

## 五、复核报告的纪律

```
[ ] 结论先行：通过 / 有条件通过 / 不通过
[ ] 新发现的缺陷逐条列出（位置 + 形态 + 修法）—— 包括自己前一轮漏的
[ ] 校验器标出的 REVIEW 项逐条定性，不能只说「已全部解释」
[ ] 已知违规如实标 exit code，不粉饰
[ ] 越界 / 不对称的口径判断全部上表交人，不自行回退
[ ] 遗留待裁决项集中成清单，注明「为什么我没自己决定」
```

**最重要的一条**：复核方与执行方**必须分离**。自己改自己审 = 用同一套错误前提验证同一套错误前提。
子代理的自检报告一律不采信，只采信机械比对结果。
