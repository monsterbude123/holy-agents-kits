# 立法协议 —— 三要素细则

规则层治理不是「把文档写得更整齐」，是**给规则本身建元数据 + 建机器抓手**。三要素缺一不可：
没有出处就没人能删（变成谁都不敢碰的存量），没有归宿就会到处复制（改一处漏三处），没有预算就必然膨胀。

---

## 一、三要素

### 1. 预算（分类上限 + 只减不增）

```
AGENTS.md < N 行          # N 取项目实际能承载的量；别拍脑袋
每 SKILL.md < M 行        # 超了就骨架化：核心留核心文件，细节下沉 references/
规则 prose 总量只减不增    # 这是唯一能真正咬住 context 的那条
```

**上限必须可达成**（2026-10-20 用户裁决，取代早期「起点 100 / 每 skill 40」的默认）：
拍一个「实测里大多数文件都超」的数，等于没约束 —— 它只能被绕过或被忽略。定上限前先量一遍白名单的
行数分布，取一个**存量里绝大多数已达标**的数。本仓实测 67 个白名单文件后定为 `AGENTS.md < 150` /
`SKILL.md < 200`。

**双阈值**（上限之上再加一道骨架化触发线）：

| 阈值 | 取值 | 含义 |
|---|---|---|
| 上限 | `N` / `M` | 目标值，超了进「未达标清单」 |
| 骨架化触发线 | `上限 × 1.25` | 越线**必须**骨架化：核心留核心文件，细节下沉 `references/` 只留指针行 |

**骨架化不是删内容**。判据是「有没有下沉」，不是「删了多少行」：细节搬到 `references/` + 原位留一行指针，
文件回到上限内，而规则一条不丢。这与「单一归宿」是同一条规则的两面。

**关键**：预算必须能验证。行数就是验证方法，`wc -l` 即可 —— 所以它天然满足「候选下沉: 可」。
但**存量超标不能靠 agent 硬删**：删正文 = 删语义 = 需人批准（见铁律「提议权」）。超标期的正确姿势是
(a) 如实披露超了多少，(b) 冻结 ratchet 防继续涨（阻断项 = 每文件实测基线），
(c) 把「距上限还差多少」列成清单（**不阻断**）供治理排期 —— 上限一旦直接当阻断线，门禁上线即红，
红的门禁会被习惯性绕过，比没有门禁更糟，(d) 出精简方案等人批。

### 2. 出处制（每条规则可溯源）

统一尾缀字段：

```
| 出处: <用户指令 / 经验账本条目编号(LRN·ERR·FEAT 等) / 经人批准的审计处置 / 存量-未溯源>
```

判据：
- **查得到** → 写具体来源，日期 + 编号 / 报告号
- **查不到** → 写 `存量-未溯源`。这是**合法且鼓励**的写法，不是失职。
- **禁止**：把「看起来像来源」的东西写成来源（校验器会判杜撰）

出处制的真实价值在半年后：有人问「这条能不能删」，看出处 —— 用户指令的要问用户，
LRN 支撑的去看教训，`存量-未溯源` 的没人敢认领 = 天然的删除候选。

### 3. 单一归宿 + 提议权

```
一条规则只有一个权威位置，其余出现一律是指针。
判归宿顺序：
  全任务底线 → 项目 AGENTS.md
  某工作流   → 对应 skill
  某目录专属 → 该目录章程
  可脚本验证 → scripts/gates/
```

**提议权**：agent 对规则层只有提议权。新增 / 修改 / 删除一律先出方案给人批。
这条是自我约束条款 —— 没有它，前面两条会退化成「agent 自己给自己立法、自己执行、自己验收」。

## 二、统一模板与口径裁定

### 模板

```markdown
- **规则一句话**（必要的括号补充） | 出处: X | 候选下沉: 可/否
```

`候选下沉: 可` = 已有或可写出脚本验证（注明是哪个 gate）；`否` = 需语义/流程判断。
**模板字段本身要能证伪**：「已下沉」的说法必须指向真实存在的脚本文件，否则就是死引用（用 `templates/check-dead-refs.sh` 扫）。

### 口径裁定表 —— 什么算「prose 规则」

判据一句话：**违反它，agent 的行为会不会变？会变 = 规则；不会变 = 描述。**

| 算规则（要转换） | 不算规则（豁免） |
| --- | --- |
| `- ` 列表项含 MUST / NEVER / 禁 / 一律 / 必须 / 不得 | 表格、代码围栏、目录树、指针表 |
| 标题即「铁律」「约定」「纪律」的整个段落 | 事实陈述（"X 有 149 个路由"） |
| 会改变执行动作的流程约束 | 能力陈述（"CLI 永远可用"） |
| 明确的命令 / 路径 / 阈值 | 排序标签（`1-2-3-5` 这类关键词列举） |
| 无列表标记但整段是祈使句规范 | 叙事段落、历史说明、版本注记 |

**灰区三连问**：
1. 拿掉这条，agent 下次会不会做错？→ 会 = 规则
2. 它是祈使句还是陈述句？→ 祈使 = 规则
3. 它的违反能被机器发现吗？→ 能 = 至少标 `候选下沉: 可`

### 转换时的三条纪律

1. **只改格式，不增删语义**。例外只有一种：新旧格式**永久互斥**（两套并存 = 矛盾），此时做**接替改写**并
   **向人披露**。这是唯一允许的语义级改动，且必须有人知情。
2. **来源括注要整段迁移**到 `出处:` 字段，不是复制。复制 = 两个权威位置 = 违反单一归宿。
   - 迁移时注意**尾部残留**：括注前常有括号/加粗包裹，剥掉内容别剥掉括号壳（`详情）` 这类）。
3. **越界与不对称都要报，不自行回退**。派发子代理时显式列「点名转换范围」；子代理超范围转换的，
   列进裁决表交人拍板。自行回退 = 替用户做决定。

## 三、转换清单的粒度

派发前必须先产出**点名清单**（不是「所有 - 开头行」）：

```
文件 · 小节号 · 该小节是否在范围 · 豁免理由
例：backend-api-dev §9「测试纪律」4 条 —— 在范围外（点名只到 §4/§6），但含 MUST 语义 → 越界，建议保留
例：session-distiller 全篇 —— 规则本体在代码围栏内 → 本轮 0 条转换，需授权才动
```

清单没产出就派发 = 把口径判断外包给子代理 = 复核期返工。
