# 实战踩坑集

每条是「现象 → 根因 → 判据 → 修法」。动手前扫一遍，能省掉整轮返工。

---

## P1 用提交区间算「源分支改了什么」会漏掉整块

**现象**：源分支有一批提交明明改了文件，合并时那些文件完全没被碰到。

**根因**：fork 历史非线性。某个区间（如 `A..B`）里的 `B` 可能是侧支上的提交，
其内容不在区间末态里；区间外的提交更不会出现在 `A..B` 的结果中。

**判据**：`git log --oneline A..B` 里出现的提交，其改动文件是否真在 `B` 的文件树里？
逐一 `git show B -- <file>` 验证。若不是，说明区间算错了。

**修法**：用集合差，不用区间——

```bash
# 源分支改过、且共同祖先没有的文件
comm -13 <(git ls-tree -r --name-only $BASE | sort) \
         <(git ls-tree -r --name-only $SOURCE | sort)
```

**典型后果**：整批 i18n key 静默缺失，切到对应语言才发现。

## P2 覆盖式回滚会吃掉未提交的合并成果

**现象**：合并脚本刚写进工作区的文件，莫名其妙回到了合并前的状态。

**根因**：`git checkout HEAD -- <path>` 是「把路径恢复成 HEAD 的内容」。
若该路径里有**尚未提交**的合并产物，它连同合并产物一起被冲掉。

**判据**：执行任何覆盖式回滚前，先确认目标路径的改动是否已提交
（`git status --short <path>` 是否显示为已暂存/已提交）。

**修法**：先提交再回滚；或用 `git restore --source=<ref> --staged --worktree -- <path>`
精确到单个文件；或用 `git reset -q HEAD -- <path>` 只清索引不动工作区。

**典型后果**：刚写入工作区的测试脚本被冲回旧版，报告在库但复跑不了。

## P3 文本行插入把 key 插到 JSON 对象外面

**现象**：JSON 解析成功、`json.load` 不报错，但读取方找不到刚插入的条目。

**根因**：用正则逐行匹配 `"key": value` 找插入点时，**顶层对象的开括号行也被匹配**
（如 `"translation": {`）。按字典序比较时，它排在多数大写 key 之后，
于是插入点落到对象外面——JSON 依然合法（顶层多了几个键），但业务读取的是
`data["translation"]`，新增的键根本不在里面。

**判据**：写完后统计**顶层键**。业务数据通常只有一个顶层键（如 locale 文件的
`translation`）。`json.load(...)` 的顶层键数异常就是中招了。

**修法**：先定位对象边界，只在边界内做键集合与插入点计算；
写完校验嵌套层级未被破坏（顶层键数 + 目标对象的条目数）。

**典型后果**：某语言界面整页回落默认语言，新增 key 全在对象外。

## P4 目标分支重写核心流程 → 源分支的逐调用点语义全丢

**现象**：合并后编译通过、测试大多绿，但某个功能「就是不生效」。

**根因**：源分支在旧版核心流程（如重试循环、错误渲染、请求构造）上挂了若干钩子，
而目标分支把那套流程整个重写了。三方合并时，源分支的钩子落在已不存在的
函数上，冲突解决时被当成「目标分支的版本」整块丢弃。

**判据**：源分支里被改过的「入口函数」，在目标分支上是否还存在同名同职责的版本？
逐个查。找不到 = 语义已丢。

**修法**：**语义移植**，不是文件覆盖。三件事一起搬：函数体、调用点、生命周期。
调用点通常在目标分支的新流程里位置不同——先读懂新流程再决定插在哪。

**典型后果**：重试、限流、指标采样上的钩子集体失联，功能看着在、实际不生效。

## P5 集合差不减「起点已有」→ 复活上游删掉的条目

**现象**：迁过去的 locale / 配置里出现了上游明明删掉的老条目。

**根因**：`新增 = 源分支最终态 − 源分支起点`。若上游在中间删掉了某个条目，
而源分支还留着旧的，这个条目就会被算成「源分支新增」而迁过去。

**判据**：逐条问——这个条目是源分支**新加**的，还是上游**删掉后源分支还留着旧的**？
后者要排除。

**修法**：`真正新增 = (源分支最终态 − 目标分支) − (源分支起点)`。
把第三项减掉，即只迁「源分支在起点之后新增、且目标分支还没有」的条目。

## P6 只迁文档不迁可执行资产

**现象**：报告、方案、索引文档全在仓库里，但里面的脚本、夹具、配置一个都没有。

**根因**：迁移时按「文档目录」取文件，把同目录下的 `.mjs` / `.py` / `.json` 当成
「工具产物」跳过了。

**判据**：每份报告/方案文档里提到的脚本、夹具、配置名，在目标分支上是否都存在？
逐个查名字。文档提到 `integration-run.mjs` 而仓库里没有，就是漏了。

**修法**：把「文档」与「它依赖的可执行资产」当成一个交付单元迁移。
迁移后用逐路径比对（`parity_check.py`）机械核对，而不是靠人读文档。

## P7 源分支脚本里的硬编码凭据跟着迁进来了

**现象**：迁入的测试脚本里带着真实 token / 密码 / 内网地址。

**根因**：源分支用「密钥扫描豁免」的方式管理凭据（gitleaks allowlist），
在源分支成立，迁到目标分支就成了明文凭据入库。

**判据**：扫描迁入目录里的 `sk-`、已知内网网段、`password:` 字面量。

**修法**：改成环境变量 + 占位符默认值；同步改写文档里的凭据声明表
（从「豁免扫描 + 列明凭据」改成「脚本内不含真实凭据 + 逐项列环境变量」）。
唯一配置源（本地排除的 `config.json`）保持不入库。

## P8 结构化文件「同 key 不同值」时不知道该取谁

**现象**：locale 里同一个 key 在两个分支上值不同，取错会让某一语言显示错文案。

**根因**：值差异往往不是「谁更新」，而是「谁的功能更全」——源分支改了功能，
文案随之改；目标分支保留的是旧功能的文案。

**判据**：看**代码实际传给翻译函数（如 `t()`）的参数**是哪一版。代码用新措辞而 locale 用旧 key，
是 key 本身该改名，不是值该改。

**修法**：以代码里实际使用的字符串为准，对齐 locale 的 **key 名**；
值保留翻译好的那一版。同时把「代码在用但 locale 没有」的 key 单独补齐。

## P9 只看「编译通过 + 测试绿」就宣布搬完

**现象**：所有门禁都过，但交付物缺了一大块。

**根因**：编译与测试只覆盖「被测到的那部分」。没被任何测试引用的新文件、
没被任何代码引用的新文案，都不会让门禁变红。

**判据**：逐路径比对目标分支与源分支在「本次要迁的范围」内是否**逐字节相同**。
不同的地方要么是有意的取舍，要么是缺口。

**修法**：把逐路径比对作为独立的验证层（`parity_check.py`），
放在「编译通过」之后、「宣布完成」之前。

---

## P10 上游删掉的能力被当成「还没做」

**现象**：规格文档写着「某能力不在本分支」，其实已经实现了。

**根因**：文档里的实现状态说明是**在合并之前**写的，合并后没回头更新。
时间顺序错了，文档就成了假信息。

**判据**：文档里的每条状态断言，逐条去代码里核一次
（符号存在吗？调用点存在吗？装配点存在吗？）。

**修法**：合并完成后，把所有「当前状态」类断言重新核一遍并改写；
只描述**行为要求与契约**的部分不要动——那是目标形态，不是现状。
