# 五层验证清单

每层问一个**不同**的问题。上一层过了不代表下一层能过。

| 层 | 问题 | 手段 | 判定标准 |
|---|---|---|---|
| 1 编译 | 代码层是否自洽 | 项目自身的构建 / 类型检查命令；多模块仓库逐模块跑 | 零错误 |
| 2 逐路径比对 | 是否**完整迁移** | `scripts/parity_check.py` | 缺失清单为空 |
| 3 语义抽查 | **功能**在不在 | 查关键符号是否存在（装配点、字段、调用点） | 逐个符号有出处 |
| 4 契约测试 | **行为**没变 | 覆盖本次迁移面的钉子测试 | 全绿 |
| 5 端到端 | **用户视角**没变 | 起真实实例跑一次关键流程 | 与源分支表现一致 |

> 第 1 层用项目自己的入口，不要照抄别的语言的命令：Go 是 `go build ./...`、
> TypeScript 是 `tsc --noEmit`（或项目脚本）、Rust 是 `cargo check`、Java 是 `mvn -q compile`。
> 多模块 / 多 workspace 仓库要逐模块跑，只跑根目录会漏掉独立模块。

---

## 第 2 层：逐路径比对

这是**唯一能发现静默缺口**的机械检查。编译与测试都发现不了「少迁了一个文件」。

```bash
python <skill-dir>/scripts/parity_check.py --repo <repo> --target main --source <source> --prefix <path>
```

比对的是「本次要迁的范围」内的路径，逐个确认目标分支上有、且内容与源分支相同。
不同的分两类：**有意的取舍**（记入台账）与**漏迁**（补迁）。

---

## 第 3 层：语义抽查

字节相同 ≠ 功能可用。目标分支重写过核心流程时（见 pitfalls P4），
源分支的钩子会静默失效——代码在，但调用点没了。

抽查对象按「功能入口」列，不按文件列：

- **装配点** —— 中间件 / 调度器 / 消费者 / 后台任务有没有在启动流程里被注册
- **配置来源** —— 上限值、开关、超时从哪来（字段？配置项？命令行参数？）
- **对外契约** —— 响应头、错误码、消息文案是否按契约发出
- **生命周期** —— 资源释放、请求作用域绑定、计数器自增

每项都要能指到**具体行号**。

---

## 第 4 层：契约测试

「契约」= 把行为钉死的测试。跑源分支的钉子测试，比跑全量测试更有信息量：
它直接覆盖了用户可见的行为。

**要跑的**：源分支带来的、覆盖本次迁移面的钉子测试
（如限流 / 队列 / 重试的槽位与错误码契约、插件的行为映射）。
全量测试也要跑，但它是排除「有没有弄坏别的东西」的兜底，不是主证据。

**平台基线要单列**：操作系统差异（临时目录占用、路径分隔符、换行符）导致的失败，
在源分支上同样失败，不算本次引入。用「在源分支上跑同一测试」的方式确认，
不要凭印象下结论。

---

## 第 5 层：端到端

只有当迁移面包含**用户可见的行为**（接口契约、错误文案、性能特性）时才必须做。
做法：在目标分支起真实实例，跑一遍源分支上跑过的关键流程，比对输出。

**黑盒数值不可原样复现**：源分支记录里的性能数字来自当时的真实环境与负载，
换环境后不可能复现同样数值。能复现的是**行为契约**（第 4 层）。
这一点要在交付说明里写清，否则会被误读成「回归」。

---

## 交付说明里必须写清的

1. 迁入的每个交付线与其范围
2. **刻意没迁的**，逐条带理由
3. 各层验证的**实际输出**（不是「已通过」三个字）
4. 平台基线失败与本次引入失败的区分
5. **无法复现的部分**及其原因（缺连接串、缺实例、缺上游服务）
6. 已知遗留项（未验证的、未修的、被上游取代的）

第 5 条尤其重要：多环境验证因缺少连接串而跳过时，
**不能声称该修复已在所有环境验证通过**。
