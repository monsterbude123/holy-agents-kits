# 选择性分支同步

两个分支差距大、用户又点名「这些不同步」时的搬运方法。

核心是三件事：**三方合并**保住目标分支的既有改动、**不同步台账**让「不迁」变成可核对的意图、
**逐路径比对**证明「该迁的都迁了、不该迁的一个没动」。三者缺一，搬运就会留下「静默的缺口」——
报告在库里但脚本没迁、代码在但文案没迁、编译过了但语义丢了。

**边界**：只管「选择性搬运」这一个动作。不管普通小差异合并、不管 PR 创建与推送、
不管上游同步策略本身该是什么。

## §1 骨架流程

| 步 | 输入 | 产出 | 谁做 |
|---|---|---|---|
| 1 立台账 | 用户点名的不同步项 + 要同步项 | 两份可逐条勾对的清单 | 主代理 |
| 2 算差异 | 目标分支、源分支 | 三类差异分类表 | 主代理 |
| 3 三方合并 | 分类表 | 干净合上的落盘 + 带标记的冲突文件 | 脚本 |
| 4 解冲突 | 冲突块 | 无标记的工作区 | 子代理 |
| 5 核对 | 目标 vs 源 | 缺失清单（该迁却漏迁的） | 脚本 |
| 6 验证 | 工作区 | 可交付状态 | 主代理 |

步骤 1 与 2 是**强制的**：不先写台账，「不同步」就只是聊天记录里的印象，
最后没人能判断某个文件到底该不该在目标分支。步骤 5 同样强制 —— 它是唯一能
发现「文档迁了脚本没迁」这类缺口的机械检查。

### 1 立台账

把用户说的「不要那些文档」「只同步 X」落成两张清单，逐条可勾对：

- **不同步清单**：路径前缀 / 文件名 / 内容特征，每条写清理由（凭据、本地专用、已被上游取代）
- **要同步清单**：同上，通常就是「不同步清单之外的一切」

不同步项若含凭据或内网地址，还要写清「迁移时如何脱敏」——这一条最容易漏。

### 2 算差异

按「谁改过」把差异分三类，三类的处理方式完全不同：

| 类 | 含义 | 处理 |
|---|---|---|
| A | 只有目标分支改过（源分支没碰） | 不动，天然保留 |
| B | 两边都改过 | 三方合并，逐块判取舍 |
| C | 只有源分支有（目标没有） | 直接取，但要过不同步清单过滤 |

**「源分支改过哪些文件」不能用提交区间算。** fork 历史非线性时（合并提交在侧支上），
区间外的提交内容不在区间末态里，用区间会漏掉整块改动。必须用集合差：
源分支最终态里改过的文件，减去共同祖先已有的文件。

### 3 三方合并

逐文件做三方合并（base=共同祖先、ours=目标分支、theirs=源分支）。
只有双方改同一行才产生冲突标记，其余自动合上——这是保住目标分支既有改动的关键。

```bash
python <skill-dir>/scripts/merge3way.py --repo <repo> --target main --source <source> --only <paths...>
python <skill-dir>/scripts/merge3way.py --repo <repo> --target main --source <source> --dry-run   # 先看分类再动手
```

脚本会把冲突文件**带 `<<<<<<<` 标记写进工作区**，交给下一步解。

### 4 解冲突

逐块按判断依据定，不要整文件取一边。判断依据见 `references/decision-rules.md`
（同一文件两边都改时谁做骨架、语义移植怎么做、结构化文件怎么合）。

解完立刻复查零残留（`git grep` 覆盖已跟踪文件，第二条兜底未跟踪的新文件）：

```bash
git grep -n -E '^(<<<<<<<|=======|>>>>>>>)' -- . ; \
  grep -rn -E '^(<<<<<<<|=======|>>>>>>>)' --exclude-dir=.git .
```

### 5 核对

搬运完做一次逐路径比对，找回「该迁却没迁」的缺口——这是本流程里唯一能
发现静默缺口的环节，也是最常被省掉的一步。

```bash
python <skill-dir>/scripts/parity_check.py --repo <repo> --target main --source <source> --prefix <path...>
```

### 6 验证

分层验证，每层问一个不同的问题，细则见 `references/verification.md`：

1. 编译（含各独立模块）——语法与类型层面
2. 逐路径字节比对——「完整迁移」层面
3. 语义抽查（关键符号在不在）——「功能在不在」层面
4. 契约测试——「行为没变」层面
5. 端到端——「用户视角没变」层面

## §2 核心逻辑

- **以目标分支为骨架，不整文件覆盖** —— 目标分支通常已含上游的新版实现，
  覆盖回去等于把上游的改进也退掉。正确做法是以目标分支为骨架，把源分支的
  **语义**移植进去（函数 + 调用点 + 生命周期），而不是复制文件。
- **源分支的「逐调用点」语义最易丢** —— 当目标分支重写过核心流程（重试循环、
  错误渲染、请求构造），源分支挂在那个流程上的每个钩子都会失联。
  判据：源分支里改过的「入口函数」在目标分支上是否还存在同名同职责的版本。
- **结构化文件用解析器合并，不用文本行插入** —— locale、schema 这类文件，
  按字典序找插入点会把 key 插到**对象外面**（JSON 仍合法，但读取方看不到）。
  必须先定位对象边界，再在对象内部按序插入，并在写完后校验嵌套层级没被破坏。
- **集合差要减掉起点已有的部分** —— 否则会把上游**主动删除**的条目复活。
  判据：这个条目是源分支新增的，还是上游删掉后源分支还留着旧的？
- **可执行资产与文档同等对待** —— 只迁报告不迁执行脚本，等于报告无法复现。
  判据：每份「报告/方案」文档提到的脚本、夹具、配置，在目标分支上是否都存在。
- **凭据一律 env 化** —— 源分支脚本里的硬编码 token/密码/内网地址，
  迁入时改成环境变量 + 占位符默认值，README 的凭据声明同步改写。
- **回滚操作会吃掉未提交成果** —— `git checkout HEAD -- <path>` 这类
  「回到 HEAD」的命令，若路径里有刚由合并脚本写入但尚未提交的内容，会一并冲掉。
  判据：执行任何覆盖式回滚前，先确认目标路径的改动是否已提交。
- **不同步台账要在收尾时重新对账** —— 「用户说不迁的」是意图，
  「实际没没迁的」是结果，两者是两个集合，收尾时逐条对账才算完成。

## §3 核心循环

搬运本身是一次性流程，真正的循环在**核对 → 补迁 → 再核对**：

```
差异分类表
   → 三方合并 → 解冲突 → parity_check
                                      │
        缺失清单非空 ─────────────────┘（补迁，再核对）
                                      │
                        缺失清单为空 ───┘
                                 ↓
                          分层验证 → 交付
```

**退出条件**：parity_check 的缺失清单为空（该迁的都迁了）、不同步台账逐条对得上
（不该迁的一个没动）、分层验证全过。

## §4 脚本

```bash
python <skill-dir>/scripts/merge3way.py --help      # 三方合并驱动（分类 + 合并 + 冲突落盘）
python <skill-dir>/scripts/parity_check.py --help   # 逐路径完整性核对，输出该迁却漏迁的清单
```
